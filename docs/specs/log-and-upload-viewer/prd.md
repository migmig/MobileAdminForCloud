## 1. 배경

`admin_golang` 서버와 웹 프론트엔드는 이미 다음 운영 기능을 제공하고 있다.

- 사용자 로그를 실시간으로 tail
- 서버 로그 4종(Backend, OAuth Resource, OAuth Auth, MobileID)을 탐색하고 열람·다운로드
- NAS 업로드 디렉터리를 탐색하고 파일 미리보기

MobileAdmin 앱이 하는 일은 사용자 로그 **파일 전체 다운로드** 하나뿐이다.

- iOS에서는 `ErrorListViewForIOS`의 카드에서 다운로드한다.
- macOS에서는 `ErrorSidebar`와 `ErrorCloudItemView.UserRow`에서 다운로드한다.

그래서 장애 대응 중에 로그를 확인하려면 PC를 켜고 웹 어드민에 접속해야 한다.

### 문제

1. **사용자 로그를 실시간으로 볼 수 없다.** 문의가 들어온 사용자의 현재 동작을 확인하려면 파일 전체를 받아 외부 앱으로 열어야 한다. 파일이 크면 모바일에서는 사실상 불가능하다.
2. **서버 로그에 앱으로 접근할 수 없다.** Backend나 OAuth 로그를 확인하려면 웹 어드민이 필요하다.
3. **업로드 파일을 확인할 수 없다.** 사용자가 올린 첨부 파일(이미지, PDF)을 앱에서 확인할 수 없다.
4. 다운로드에 실패해도 iOS에서는 오류가 표시되지 않고 조용히 무시된다(현행 버그).

## 2. 목표 / 비목표

### 목표

| ID | 목표 |
|---|---|
| G1 | 사용자 번호만 입력하면 해당 사용자 로그를 앱에서 **실시간 스트리밍**으로 볼 수 있다 |
| G2 | 서버 로그 4종을 **폴더 → 파일 → 내용(마지막 N줄)** 순서로 탐색·열람·다운로드할 수 있다 |
| G3 | NAS 업로드 디렉터리를 탐색하고, 이미지·PDF·텍스트 등을 **앱 안에서 미리보기**할 수 있다 |
| G4 | 세 기능 모두 iOS와 macOS를 지원하며, 플랫폼별 관례(iOS 드릴다운 / macOS 3단 분할)를 따른다 |
| G5 | 실패하면 원인(파일 없음, 권한, 서버 미지원 등)을 화면에 표시한다 |

### 비목표 (v1 범위 제외)

- **로그 파일 정리**(`/log/*/organize`): 서버 파일을 이동하는 변경 작업이라 모바일에서 오조작 위험이 크다.
- **ZIP 일괄 다운로드**(`/log/*/zip`): 다중 선택 UI와 대용량 스트림을 다뤄야 한다. v2에서 macOS 전용으로 검토한다.
- 업로드 파일의 업로드, 삭제, 이름 변경: 서버 API가 없다.
- 로그 내용 서버 측 검색(grep): 서버 API가 없다. 받은 범위 안에서만 클라이언트가 검색한다.
- 푸시 알림 기반 로그 감시, 백그라운드 스트리밍.
- 기존 토스트 시스템 수정. iOS에서는 토스트가 표시되지 않는 현행 문제가 있지만 이번 범위가 아니다. 이번 기능은 토스트에 의존하지 않는다.

## 3. 사용자와 시나리오

**사용자:** 내부 운영자와 개발자. 소수이며 모두 관리자 권한을 갖는다. 앱 진입 시 생체 인증(iOS)을 거친다.

### 시나리오 S1 — 사용자 문의 실시간 대응 (G1)
> 운영자가 "본인인증이 계속 실패한다"는 전화를 받는다. 앱에서 **사용자 로그**를 열고 사용자 번호 `109114`를 입력한 뒤 **시작**을 누른다. 최근 200줄이 바로 표시되고, 사용자가 재시도하는 동안 새 로그가 실시간으로 이어진다. 에러 줄을 길게 눌러 복사한 뒤 개발자에게 전달한다.

### 시나리오 S2 — 야간 장애 원인 확인 (G2)
> 개발자가 오류 알림을 받는다. 앱에서 **서버 로그 → Backend**를 열고 환경을 `gcgf-untact`로 선택한다. 루트 폴더에서 가장 최근 파일을 열어 마지막 1000줄을 보고, `Exception`을 검색해 위치를 찾는다. 더 넓은 범위가 필요하면 tail을 5000줄로 늘린다. 원본이 필요하면 파일을 다운로드해 공유한다.

### 시나리오 S3 — 업로드 첨부 확인 (G3)
> 운영자가 "서류를 올렸는데 반영이 안 된다"는 문의를 받는다. 앱에서 **업로드 파일**을 열어 해당 디렉터리로 이동한다. 업로드된 `scan.pdf`를 탭해 Quick Look으로 내용을 확인한다.

### 시나리오 S4 — 오류 목록에서 바로 로그 보기 (G1, P2)
> 오류 상세에 표시된 사용자 ID 옆의 **실시간 로그** 버튼을 누르면, 해당 사용자의 tail 화면이 바로 열린다.

## 4. 기능 요구사항

우선순위 정의:
- **P0**: v1 출시에 필수.
- **P1**: v1에 포함을 권장.
- **P2**: 여유가 있을 때 진행.

## 5. 비기능 요구사항

| 구분 | 요구사항 |
|---|---|
| 성능 | 목록 응답은 받은 지 300ms 안에 렌더링한다. 로그 내용 10,000줄을 표시해도 스크롤이 끊기지 않는다(LazyVStack 사용) |
| 성능 | tail 수신 중 UI 갱신은 최대 초당 약 7회(150ms 주기 배치)로 제한한다 |
| 메모리 | tail 버퍼는 최대 5,000줄이다. 파일은 메모리에 올리지 않고 디스크로 직접 내려받는다(`URLSession.download`) |
| 네트워크 | tail 스트림은 서버가 heartbeat를 보내지 않으므로, 요청 타임아웃을 충분히 길게(1시간) 잡는다 |
| 보안 | 로그에는 개인정보가 들어 있다. 받은 로그 내용을 앱 Logger에 기록하지 않는다 |
| 보안 | iOS에서 받은 파일은 Caches 아래 앱 전용 경로에 저장하고, 앱을 시작할 때 24시간 지난 파일을 삭제한다 |
| 보안 | macOS에서 받은 파일은 사용자가 명시적으로 다운로드한 것이므로 `~/Downloads`에 보존한다 |
| 호환성 | iOS 17.6+, macOS 14.6+. 새 외부 의존성을 추가하지 않는다 |
| 일관성 | 기존 디자인 토큰(`AppDesign.swift`)과 `EmptyStateView`, `.loadingTask`, `.refreshable` 패턴을 그대로 쓴다 |
| 언어 | UI 문자열과 주석은 한국어로 작성한다(기존 관례) |

## 6. 성공 지표

내부 도구라서 정성 지표가 중심이다.

- 장애 대응 시 PC나 웹 어드민 없이 앱만으로 로그를 확인할 수 있다(S1, S2 시나리오 수행 가능).
- 사용자 번호 입력부터 첫 로그 줄이 표시되기까지 3초 이내(사내망, 정상 서버 기준).
- 서버 로그 파일을 선택한 뒤 1000줄이 표시되기까지 3초 이내(비압축 10MB 파일 기준).
- 다운로드와 조회가 실패하면 100% 화면에 원인이 표시된다(조용히 실패하는 경우 0건).
